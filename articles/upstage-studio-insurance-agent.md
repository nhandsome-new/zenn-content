架空の損害保険会社を一社立てて、そこでヒアリングをしたらこういう要件になるだろう、というものを文書にまとめました。そしてその要件書を、そのまま Upstage Studio に入れています。ノードを一つずつ並べていないのにパイプラインができあがり、内容の異なる書類一式で7回動かした結果まで合わせて整理します。

---

## Upstage Studio — 文書処理に特化したエージェントビルダー

Upstage Studio は、文書を扱うエージェントを作るためのツールです。画面で確認できるノードは、パース（Parse）、分類（Classify）、抽出（Extract）、指示（Instruct）、検証（Validate）、マージ（Merge）の6種類でした。

**この6つが文書処理の骨組みで、今回作ったものも結局はこのノードの組み合わせです。**

https://studio.upstage.ai/

## シナリオ — ボトルネックは書類の束を前にしたところで起きる

シナリオはこうです。自動車事故が起きると、請求者から書類が一式まとめて届きます。種類も枚数も毎回違います。担当者はその束を前にして、次の4つを手で行います。

1. **仕分ける** — 請求書、事故状況報告書、保険証券、診療費明細書、領収書、修理見積書…と種類ごとに分ける
2. **読み取る** — 書類ごとに必要な値を探して書き写す
3. **照合する** — 約款の条項を一つずつ当てて、支払えるかどうかを見る
4. **書く** — 判定と根拠、支払額をまとめた審査報告書を作成する

**1件届くたびに、この4つがまるごと人の手に乗ります。** ここがボトルネックです。

さらに束の中には、審査と関係のない書類が混ざって届きます。行政機関からの調査文書や、審査とは無関係の健康診断書類といったものです。こうした書類は審査のパイプラインでは処理できないので、分類の段階で切り分けて担当部署へ回す必要があります。

判断ルールは概要だけ整理しました。書類が揃っているか、約款6か条を満たすか、どの部署へ回すかの3つです。

![](/images/upstage-studio/workflow-ja.png)

## 用意したもの — 要件書とダミー書類一式

入力は2つです。業務の流れ、書類の種類、書類ごとに取り出す情報、判断ルールをまとめた要件書。そして、その要件を試すためのダミー書類一式です。

書式と記載項目だけを実物に近づけたダミーデータを生成しました。種類は8つに分かれます。保険金請求書、事故状況報告書、保険証券、診療費明細書、領収書、修理見積書、行政照会、その他の文書です。

**要件書で一番手間がかかったのは、書類ごとに取り出す情報を個別に決める部分でした。** 保険証券からは証券番号、保険期間、運転者年齢条件、免責金額を取り出し、領収書からは病院名、通院日数、領収金額、期間を取り出します。

![](/images/upstage-studio/documents-8classes-ja.png)

## やったこと — 要件とサンプルの投入、そして一度の修正

要件書とサンプル資料をそのままチャットに入れました。ノードを一つずつ配置していないのに、エージェント設定の下書きができあがっていました。

生成された構成はこうです。書類を8種類に仕分ける分類ノードが1つ、書類の種類ごとの抽出ノードが7つ（行政照会とその他の文書は取り出す項目が同じなので1つにまとまりました）、複数の書類を1つにまとめるマージ、判断ノードが3つ（書類の充足、約款照合、部署への回送）、そして報告書・見積要約票・回送案内を書く文章生成ノードが3つです。

![](/images/upstage-studio/studio-01-agent-created.gif)

Studio は、できあがったエージェントをノードグラフで表示します。パースから分類、抽出、マージへとつながる流れが目に見えるので、何がどうつながっているかを確認できました。

ノードを一つずつ見ていくと、複数の書類の情報を1つにまとめて判断する場所が空いていました。その点をチャットで指示したところ、エージェント設定が生成し直され、ノード構成が更新されました。画面には設定7件が変更されたと表示されています。

**こちらが直したのはこの一か所だけで、それもノードを編集したのではなく、自然言語で指示しただけです。**

![](/images/upstage-studio/studio-02-chat-patch.gif)

最後に、整理しておいた業務の流れと一致するか、細かい要件が資料と合っているかを確認しました。流れにずれはなく、要件書に書いた判断基準もそのまま反映されていました。

## 別の書類で7回動かしてみた

エージェントを作るときに使ったテンプレートを含め、内容の異なる7種類で動かしました。作成時のサンプルだけを確認するのではなく、構成の違う書類一式を個別に入れて、結果がどう変わるかを見ています。

書類一式をまとめて入れると、ページ単位で仕分けられます。11ページの束からは、審査対象の6種類と、審査に関係のない行政照会2枚・その他1枚が自動で分かれました。

![](/images/upstage-studio/studio-03-run-verify.gif)

入力された書類の特徴ごとに、どう判断して処理したか、その理由をまとめると次のようになります。

| 入力書類の特徴 | 判断とモデルの提案 | その理由 |
|---|---|---|
| 請求書・事故報告書・証券・診療費関係の書類・見積書がすべて揃った基本形 | 一部支払可能 | 治療費は算定できるが、車両修理費は見積の妥当性をアジャスターが確認する必要がある |
| 事故日が保険期間を外れているもの | 支払不可 | 第1条 — 保険期間外の事故 |
| 請求項目に対応する証憑が欠けているもの | 書類不備 | 追加書類がなければ審査を進められない |
| 事故時点の運転者の年齢が証券の条件と食い違うもの | 追加確認 | 判断を確定するには関連規定がさらに必要 |
| 飲酒運転の記載があるもの | 支払不可 | 第6条 — 免責事由 |
| 行政機関から届いた調査文書 | 照会対応室へ回送 | 審査対象ではない行政の照会・調査文書 |
| 審査と関係のない健康診断書類 | 回送先の判定を保留 | 具体的な依頼内容や照会事項が確認できない |

成果物は判定、見積、回送の3種類に分かれます。

**判定**は、約款の条項を一つずつ照合した根拠がまず並び、そのあとに判定と支払額、次に行うこと、担当者確認欄が続きます。

![](/images/upstage-studio/result-judgment.png)

**見積**は、項目ごとの修理方法と金額が表にまとまり、合計が出ます。最後に、支払可否と金額の妥当性は判断していないと明記されます。修理見積の妥当性はアジャスターが確認するものと要件書で決めていたのですが、その線引きが成果物にそのまま書かれた形です。

![](/images/upstage-studio/result-estimate.png)

**回送**は、審査対象ではない文書を担当部署へ回す処理です。行政機関から届いた調査文書は照会対応室へ回すと判定し、健康診断書類のほうは回送先を決められず保留にしました。

![](/images/upstage-studio/result-routing.png)

**そして、これらの出力はすべて、文ごとに根拠となった文書の引用番号を伴って出てきます。** 判定がどの書類のどの値から出たのかをたどれます。

## やってみて分かった制約

結果を読むときに、合わせて見ていただきたい範囲があります。

- **合成データです。** 実際の保険会社の書類ではなく、書式だけを似せたダミー7セットで動かしています。
- **精度のベンチマークではありません。** 何パーセント当たるかを測る実験ではなく、要件書のとおりにパイプラインが立つかを見たものです。
- **人が途中で確認しています。** 最初の生成のあとにノード構成を自分で確認し、マージの部分は一度修正を指示しました。
- **7件の結果が自動化率を意味するわけではありません。** ケースごとに分岐が正しく分かれるかを確認したところまでです。

## やってみて考えたこと

**エージェントを一つずつ組み立てるツールではなく、要件さえはっきりしていれば対話しながらエージェントができあがる方向へ進化していました。** 最近の流れと同じ向きです。こちらがやったのはノードを並べることではなく、何が必要かを整理することでした。

要件がノードとして可視化されるので、どこがおかしいかがすぐ見えました。複数の書類をまとめて判断する場所が空いていたことも、グラフを見て気づいたものです。直す場所を探すのに時間はほとんどかかりませんでした。

流れを中心に据えた構造なので、今後こまかい判断に手を入れるときに、どこを直せばよいかも一緒に見えました。約款の条項を一つ変えるならどのノードを開くのか、が目に入るという意味です。
