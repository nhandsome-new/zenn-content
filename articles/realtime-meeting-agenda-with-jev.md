ミーティングのアジェンダを練って決めておいたのに、いざ会議が終わってみるとそのうち一つをまるごと忘れていたり、結論が出ないまま終わっていたり。そういう経験、ありませんか。

作ってみたのがこれです。**ワークショップ準備のオンライン会議**で、**アジェンダは日程・予算・会場・プログラム・役割の5件**です。会議が進むあいだ、5つの信号がそれぞれ変わります。

## 会議が終わる前に知りたいこと

議事録の要約はもうたくさんあります。ただ要約は、**会議が終わったあとに**出てきます。

困るのは会議の最中です。3つ目のアジェンダで話が長くなり、気づけば残り10分。終わってから「あれ、やってなかった」と分かっても手遅れです。**時間が残っているうちに分かってこそ**、手の打ちようがあります。

そのためには会議のあいだ、問い続ける必要があります。問い続けるには、まず **速い** こと。30秒ごとに問いかけて答えが10秒後に来るなら、それはもう過ぎた会議への答えです。そして **安い** こと。会議1回で数十回は呼ぶのですから。

Jev はちょうどその二つを満たしていました。

## アジェンダがどこまで進んだかを信号で示す

アジェンダ一つがいまどの段階にあるかを、三つに分けて見せます。

| 信号 | 意味 |
|---|---|
| 🔴 | まだ話していない |
| 🟡 | 話したが、明確な結論がない |
| 🟢 | 明確な結論が出て、いまも有効 |

🟡 には先送りと撤回がまとめて入ります。「それは次回に決めましょう」も、決めたあとに撤回したものも、結論がない状態であることは同じだからです。

モデルに送るのはこれで全部です。

```python
Choice(
    instructions={
        "agenda": {"id": "A2", "title": "Budget",
                   "description": "How much money can be spent on the workshop."},
        "question": "What is the status of `agenda` in `transcript`?",
    },
    criteria={
        "red": "Not talked about yet. The same words used about something else do not count.",
        "yellow": "Talked about, but there is no clear conclusion yet. This includes putting it off, "
                  "or taking back an earlier conclusion.",
        "green": "A clear conclusion was reached, and it still stands.",
    },
)
```

役割の指示も、出力形式の説明も、例もありません。**選択肢三つに一行ずつ付けたのがプロンプトのすべて**です。

そして **アジェンダごとにこの質問を一つずつ付け、一度のリクエストで送ります。** アジェンダが5件なら質問も5件ですが、呼び出しは1回で、互いに干渉しません。**アジェンダが増えても呼び出しの回数は変わりません。**

`state` には会議の最初からいままでの台本をまるごと入れます。

```json
{"transcript": [{"speaker": "Emily", "text": "予算はいくらまで出せますか？"}, ...]}
```

考えた構造を一枚にまとめると、こうなります。

## まずテキストで測った

音声を付ける前に、テキストだけで確かめました。**20分の会議台本を5本**書き、**1分単位で切って、その時点までの台本だけ** Jev に入れました。アジェンダが5件なので会議1本で100判定、1言語あたり **500判定** です。

台本はワークショップ準備の3本（うまく進んだ会議 / 時間が足りない会議 / 雑談と撤回の多い会議）、オフィス移転、新入社員の受け入れ準備です。

| 指標 | 日本語 | 英語 | 韓国語 |
|---|---|---|---|
| **各判定時点の正解** | **492/500（98.4%）** | **491/500（98.2%）** | **489/500（97.8%）** |
| 最終信号の正解 | 25/25 | 25/25 | 23/25 |
| 信号の切り替わり検出 | 30/31 | 30/31 | 30/31 |
| 検出の遅れ（中央値） | 36秒 | 37秒 | 36秒 |

3言語の差はほとんどありませんでした。

### 引っかけも一緒に評価した

単にキーワードを数えるのと区別するため、台本に難しい場所を14か所仕込んでおきました。分かりやすいものだけ挙げるとこうなります。

| 引っかけ | 台本で起きること | 正解 |
|---|---|---|
| 言葉はなく結論だけ | 「予算」という単語が一度も出ないまま、1人あたりの金額が決まる | 🟢 |
| 言葉はあるが別の話 | アジェンダは「新入社員の研修日程」なのに、台本には全社のセキュリティ研修の話しか出ない | 🔴 |
| 決めてから戻す | 日程を決めたあと、また保留に戻す | 🟡 |
| 戻したあと決め直す | 保留になっていた日程が、あとで改めて決まる | 🟢 |

**引っかけ14件のうち、日本語と英語は14件すべて、韓国語は13件を通過しました。**

間違えたものには偏りがありました。**結論が出る直前に先回りして🟢を灯す**ケースが最も多かったです。まだ終わっていないものを終わったと見なす方向なので、実際に使うなら🟢はもう1ティック待ってから灯すほうが安全そうです。

## 全部送るか、直近だけ送るか

会議が長くなるほど台本は積み上がります。**毎回すべてを送り直すのか**が分かれ道でした。

![二つの方式の比較。5分時点で予算が決まった会議を15分時点でもう一度判定させたとき、全文を送れば🟢が保たれるが、直近3分だけ送るとその決定が窓の外に出て🔴に戻ってしまう。各判定の正解率は98%対82%。](/images/agenda-signal/agenda-signal-window-ja.png)

直近3分だけ送るほうは、**直前の判定結果も一緒に渡していたのに**戻ってしまいました。目の前の3分にそのアジェンダの話がないので、まだ触れていないものとして読んだわけです。

**覚える仕事をモデルに任せたのが設計ミスでした。** 状態はコードが持つべきものでした。

そのため以降は全文を送るほうだけを使いました。ただし会議が長くなればこちらも問題になります。直し方は見えています。信号はコードが持ち、Jev には直近の区間で **変わったものがあるかだけ** を問う形です。今回は実装していません。

## リアルタイムで回してみた

テキストで数字が出たので、音声を付けました。台本を TTS に読ませて会議の音声を作り、リアルタイムで入ってくるように流しました。**30秒ごとに**そこまで聞こえた音声をローカルの Whisper（`whisper-large-v3-turbo`、MLX）で文字起こしし、その全文で Jev が判定します。Mac Studio で動かしました。

| | 日本語 | 英語 |
|---|---|---|
| 音声の長さ | 9分50秒 | 11分20秒 |
| 判定回数 | 20 | 23 |
| 各判定時点の正解 | 97/100 | 112/115 |
| 最終信号の正解 | 5/5 | 5/5 |
| 30秒あたりの最大処理 | ASR 1.1秒・Jev 0.7秒 | ASR 1.1秒・Jev 0.6秒 |

**30秒分を2秒以内に処理します。** 次の30秒が来るまで28秒残るので、この Mac ではリアルタイムで回ると見てよさそうです。

正解率もテキストだけを入れたときとほぼ同じです。**文字起こしが多少ずれても信号は崩れませんでした。**

最初に立てた前提が「安い」だったので、そちらも確かめました。

| 項目 | 値 |
|---|---|
| Jev 呼び出し1回 | 平均およそ0.27秒（上位5%で約0.33秒） |
| 20分の会議1件（1分ごと） | 約 **$0.003** |
| 料金 | 入力100万トークンあたり $0.042、出力は無料 |

**会議1回で0.3セント。** つけっぱなしにして忘れてよい水準です。

## では実際に使うには

実際の会議に載せる道は二つ見えます。**Zoom や Teams のリアルタイム字幕を受け取るか**、**システム音声を直接取ってローカルで文字起こしするか。** 今回のデモは後者に近い形です。

ただ、どちらにしてもその先でつまずきます。**業務会議の内容を外部の API に送ることはできません。** 文字起こしだけをローカルにしても意味がありません。**Jev が判定するには**、結局その台本が外に出ることになるからです。

そこで次は **ローカルで動く判断モデル**で同じことを試すことになりそうです。判定の部分だけ差し替えれば済むように作ってあるので、正解率と速度がどこまで追いつくかを見るだけです。

:::message alert
**この実験の限界**：20分の会議でしか確かめていません。会議が長くなると呼び出しごとの入力が大きくなり（今回の台本で1分あたり約235トークン）、入力の上限・正解率・費用・遅延がどうなるかは**今回扱っていません。** 台本はすべて架空で、実際の会議より発話の密度が低めです（20分で3,100〜4,000字）。正解ラベルは一人が付けたもので、人による検収は通していません。🟢の時点を数秒動かすだけで数字が変わります。実行ごとに ±1〜2 程度の変動があります。
:::
