거창한 계기는 없었어요. 그냥 나만의 에이전트를 하나 갖고 싶었고, 이번이 그 첫 시도였습니다.

개인 서버를 하나 구매해서 관리하다가, 첫 시도로 `agentic_env`라는 이름의 개인 비서 환경을 만들어봤습니다. 역할·폴더·기록 방식을 문서로 고정해서, 여러 모델을 역할별로 나눠 쓰는 구조예요.

---

## 역할을 넷으로 나눴어요

핵심 아이디어는 단순합니다. **일이 모호할 땐 더 똑똑한 모델이, 절차가 안정되면 더 가벼운 모델이 맡는다.** 지금은 4단계로 나눠서 씁니다.

```mermaid
flowchart LR
    A["기획<br/>Claude Opus"] --> B["운영<br/>Claude Sonnet"]
    B --> C["안정화<br/>Solar Pro4"]
    C --> D["반복 실행<br/>로컬 모델"]
```

| 단계 | 모델 | 하는 일 | 구동 방식 |
|---|---|---|---|
| 기획 | Claude Opus | 모호한 아이디어 정리, 새 작업의 설계 문서 작성 | Claude Code에서 직접 대화 |
| 운영 | Claude Sonnet | 일상적인 정리, 작업 배분, 진행 상황 점검 | Claude Code에서 직접 대화 |
| 안정화 | Solar Pro4 | 기획 결과를 실제로 돌려보며 대화형으로 다듬기 | `Hermes`에서 직접 대화 |
| 반복 실행 | 로컬 모델 | 절차가 굳은 뒤 무한 반복 | `Hermes` CLI, 자동 배정 |

기획·운영은 Claude Code 안에서 제가 직접 모델과 대화하면서 다룹니다. `/model` 명령으로 오퍼스↔소넷을 그때그때 전환해요.

안정화와 반복 실행은 `Hermes`로 관리되고 돌아갑니다. Solar는 안정화 단계 특성상 저와 대화를 자주 나누는 편이고, 로컬 모델은 대화보다 정해진 절차를 반복 실행하는 용도로만 쓰고 있어요.

로컬 모델을 마지막에 둔 이유는 두 가지예요. **비용이 안 들고, 데이터가 기기 밖으로 안 나갑니다.**

## Solar Pro4에게 기대하는 것

한국어와 일본어가 **공식 지원 언어**라는 게 가장 컸습니다. 평소에 두 언어를 다 자주 쓰는 입장이라 이 부분은 특히 기대가 됐어요.

:::message
Solar Pro4는 지금 **무료 체험 기간**이라 8월 10일까지 무료로 쓸 수 있습니다.

https://console.upstage.ai/docs/models/solar-pro-4
:::

:::details 그 외에 눈여겨보고 있는 스펙들
- **컨텍스트가 넉넉합니다.** 공식 문서 기준 512K 컨텍스트, 출력은 최대 128K 토큰까지 지원합니다. 숫자상으로는 꽤 여유로운 편이라, 긴 문서를 통째로 넣고 분석을 맡기는 일도 한번 시켜볼까 싶어요.
- **툴콜(에이전틱) 기능을 공식 지원합니다.** "Upstage의 플래그십, 에이전틱 특화 모델"이라고 소개하고 있고, 전작 대비 에이전트 성능이 크게 개선됐다고 밝히고 있어요. 아직 많이 써보면서 분석해보진 않았지만 기대하고 있습니다.
:::

## 개인 데이터는 로컬에만

원리는 간단해요. 진짜 개인 데이터는 로컬 모델만 보게 해뒀고, 클라우드 쪽(Claude, Solar)은 아예 접근을 막아놨습니다. 기획·설계 단계에서는 구조만 같고 내용은 가짜인 샘플 데이터를 대신 씁니다.

## 폴더는 최대한 단순하게

폴더 구조는 이렇게 생겼습니다. 작업 환경과 데이터 저장소를 나눠둔 게 전부예요.

```text
~/agentic_env/
  harness/            # 운영 규칙 + 공용 도구 + 표준 양식
  projects/<이름>/    # 프로젝트별 기획서 + 작업 기록 + 결과물
  inbox/              # 일단 아무거나 던져두는 곳

~/data/
  personal/           # 진짜 개인 데이터 — 로컬 모델만 접근
  personal_mock/      # 가짜 샘플 데이터 — 기획·설계용
  public/             # 공용 자료 — 어느 모델이든 접근 가능
```

새 작업을 시작할 때마다 폴더 구조를 매번 새로 고민하지 않도록 기본 양식을 미리 만들어놨습니다. 복사해서 시작하면 끝이에요.

모델들은 서로 실시간으로 대화하지 않습니다. 기획 단계에서 설계 문서를 남기면, 다음 단계가 그걸 읽고 작업한 뒤 기록을 남기는 식이에요.

세션이 끝나면 그 안의 기억은 사라지기 때문에, **문서에 안 남은 결정은 다음 세션엔 없던 일이 됩니다.** 그래서 작업이 끝나면 매번 git으로 커밋해두는데, 커밋 메시지 앞에 역할을 붙여둡니다.

```text
[기획]   insight-brief 설계 문서 작성
[안정화] 프라이빗 폴더 접근 차단 테스트 추가
```

나중에 봐도 뭐가 언제 바뀌었는지 바로 보여요.

## 처음 만들어본 도구, `insight-brief`

정보원(링크·PDF·텍스트)을 대충 던져두면 브리핑 자료 한 장을 만들어주는 도구입니다. 명령 한 줄로 끝나고, 실행 중엔 아무것도 안 물어봐요.

사실 엄청 자주 쓸 기능은 아니고, **Solar Pro4가 기획부터 코드 작성, 실행까지 어디까지 스스로 해내는지 보려고 만든 쪽에 가깝습니다.** 만드는 주체이자 실행하는 주체가 둘 다 Solar였어요.

구조도 단순해요. `insight_brief/`라는 파이썬 패키지 안에 소스 읽기, 프롬프트 구성, 생성·검증까지 딱 5개 파일, 800줄 남짓이 전부입니다. 코드가 하는 일은 원문을 긁어오고 프롬프트를 조립하고 결과를 검증하는 정도이고, 정해진 형식(프론트매터 + 한 줄 요약·핵심 포인트·상세·시사점 4단 구성)을 지키면서 실제 글을 쓰는 건 전부 Solar Pro4가 호출 한 번으로 처리합니다.

중간에 사람이 손대는 구조화 단계 없이 이 정도 복잡도의 글쓰기를 한 번에 해내는지가 이번 테스트의 핵심이었어요.

**테스트한 것**

- URL 입력, PDF 입력, 텍스트 입력 — 각각 여러 번 돌려서 결과가 매번 같은 형식으로 나오는지 확인
- 프라이빗 폴더 — 클라우드 모델이 개인 데이터에 접근하는지 안 하는지 확인 (결과는 아래에)

## 데이터 분리 원칙이 실제로 걸리는지 확인

말로만 있는 원칙인지 직접 시험해봤어요. 서로 다른 파일 두 개를 각각 프라이빗 폴더와 퍼블릭 폴더에 넣어두고, 에이전트에게 둘 다 브리핑해보라고 시켰습니다.

| 파일 위치 | 쓰려던 모델 | 결과 |
|---|---|---|
| 퍼블릭 | Solar Pro4 (클라우드) | ✅ 브리핑 생성 성공 |
| 프라이빗 | Qwen (로컬 / Rapid-MLX) | ✅ 성공 — 파일 종류와 상관없이 접근됨 |
| 프라이빗 | Solar Pro4 (클라우드) | ❌ **실패.** 접근해도 되는지 오너의 지시가 필요하다는 메시지만 뜨고 멈춤 |

로컬 모델은 파일이 뭐든 상관없이 접근했지만, 클라우드 쪽은 프라이빗 폴더 앞에서 막혔습니다. 의도한 대로 작동한 셈이에요.

지금은 딱 여기까지입니다. 이 구조로 더 오래 굴려본 경험은 이제부터 쌓일 예정이에요.
