:::message
**3行まとめ**
- プログラムが必要なのは `if` 一つなのに、私たちはLLMに文章を作らせ、その文章をまた `if` に戻しています
- `Jev` は文章を一切作らず、**判断と確率**だけを返すモデルです。その設計を整理しました
- 同じ質問をJevとオープンソース実装（SemIf）の両方に投げた結果も載せています

サポートチケットをどのチームに送るか決めるコードを考えてみます。プログラムが知りたいのは、結局この一行です。

```python
if department == "billing":
```

ところがLLMにやらせていることはこうです。プロンプト → 文章生成 → JSON → スキーマ検証 → パース → 失敗したら再試行 → ようやく `if`。**必要なのは値一つなのに、文章を一周しました。**

## Jev：文章の代わりに確率を返すモデル

この問題を正面から取り上げたのが、TypeSafeという会社の `Jev` です。公式ドキュメント（[docs.typesafe.ai](https://docs.typesafe.ai/introduction)）の表現が直球です。

> テキスト生成もパースもない。コードがそのまま分岐し、ソートし、ルーティングできる型のある値と確率分布を受け取る。

使い方からして違います。プロンプトを文章で組み立てません。アプリケーションがすでに持っているJSONを **state** としてそのまま渡し、その状態について **聞きたいことを型で** 定義します。

```python
response = client.system_one(
    state=ticket,                   # アプリのJSONをそのまま
    questions={
        "department": Choice(...),  # どのチームへ送るか
        "frustration": Score(...),  # 不満度はどのくらいか
        "is_urgent": Noul(...),     # 緊急か
    },
)
response.answers["is_urgent"].noul  # 0.94
```

ふだんはDBにある値を、わざわざ文章に書き下してプロンプトに入れます。

```text
顧客のプランはenterpriseで、国は日本です。
注文A-104に49ドルの決済が2件あり、どちらもcaptured状態です。
重複決済は返金ポリシー上、返金対象です。
顧客は「49ドルが2回請求されたので、重複分を早く返金してほしい」と書いています。
```

ところがアプリケーションには、すでにこれがあります。

```json
{
  "ticket": {
    "subject": "Charged twice for one order",
    "message": "I was charged 49 dollars two times for order A-104.
                Please refund the duplicate as soon as possible."
  },
  "customer": { "plan": "enterprise", "country": "Japan" },
  "order": {
    "id": "A-104",
    "charges": [
      { "amount": 49, "status": "captured" },
      { "amount": 49, "status": "captured" }
    ]
  },
  "refund_policy": { "duplicate_charge": "eligible" }
}
```

このチケットは、後ほど実際にJevとSemIfへ送ったものでもあります。

後者は **構造がそのまま情報** です。`charges` が配列で要素が二つあるという事実そのものが「二回請求された」を語ります。

文章に書き下すと、この構造をモデルが読み直して組み立て直さなければなりません。そして答えはまたJSONでくれと頼むわけです。**Jevはその往復をなくします。**

質問を複数、**一度に、互いに独立して** 送るところも見どころです。上のコードで `frustration` は `department` が何になったかを知りません。三つの質問がそれぞれ同じチケットだけを見て別々に答えます。

よく使うやり方は違います。一度答えさせ、その答えを入れて次を聞き、またその答えを見て判断します。

![続けて聞くと別々に聞く：連鎖方式は前の答えが次の質問に入りリクエストが3回だが、Jevは同じ状態を三つの質問がそれぞれ読むのでリクエストは1回で、互いの答えを知らない。](/images/semantic-if/semantic-if-independent-ja.png)

独立していれば、前の判断が間違っても **後ろに広がらず**、一つを直しても残りがぶれません。おかしな答えが出たら **その質問だけ** を見ればいいのです。

代わりに、組み合わせはコードの仕事です。

```python
if category == "billing": ...
if urgent > 0.8:      priority += 1
if frustration > 1.5: priority += 1
```

だから **AIが制御フローを持ちません。** いまのエージェントはモデルが考え、ツールを選び、また考える形なので、流れをモデルが握ります。Jevは逆です。順序・しきい値・重みはコードに残り、モデルは自然言語を読む狭い判断だけを引き受けます。基準が変わればプロンプトを組み直す代わりに、数字を一つ直します。

## 三つの判断：Choice・Score・Noul

Jevは判断を三種類にだけ分けます。小さくて組み合わせられる部品に近いものです。

| | 使いどころ |
|---|---|
| **Choice** | 順序のない候補から一つ（billing / access / technical） |
| **Score** | 順序のある尺度（平静 → 不快 → 不満 → 怒り） |
| **Noul** | 命題が真か（返金を求めているか） |

先ほどのチケットに三種類を一度に聞いたら、こう返ってきました。

```json
"queue": {
  "choice": "billing",
  "confidence": 1.0,
  "probabilities": { "billing": 1.0, "technical": 0.0, "access": 0.0 }
}

"frustration": {
  "score": 0.71,
  "confidence": 0.6,
  "legend":        { "0": "Calm", "1": "Annoyed", "2": "Frustrated", "3": "Angry" },
  "probabilities": { "0": 0.34,   "1": 0.61,      "2": 0.05,         "3": 0.0 }
}

"refund": { "noul": 0.99 }
```

**Choice** は選んだ値だけでなく、候補ごとの分布をまるごと返します。1位だけを見ることも、2位との差が小さいときだけ人に回すこともできます。

**Score** の `0.71` は整数レベルではありません。*Calm* 0.34 に *Annoyed* 0.61 が乗っているので、二つの間に落ちた値です。ドキュメントの言う *「レベルとレベルの間」* がこれです。`legend` が一緒に来るので、その数字が何を指すかも分かります。

**Noul** はフィールドが一つだけ。`confidence` がありませんが、確率そのものが確信なので別に返すものがないわけです。もっとも `if` に近い形です。

ここから出てくる原則が **質問を細かく割れ** というものです。「リスクを評価して、どのチームがどの優先度で処理するか決めろ」のような大きな質問ではなく、小さな質問を複数に。そうすればそれぞれを別々に見て直せます。

## 0.9が90%になるように：RLCD

確率を値として使うには、引っかかる問題があります。モデルが `0.9` と言ったとき、本当に10回に9回当たるという意味なのか。

実務でしきい値を引くのがしんどい理由がここにあります。**`0.8` という数字に意味がないので**、ラベルを付けたデータを集めて0.7でやってみて0.85でやってみて、と線を探します。タスクが変われば最初からやり直しです。

> 確率 `0.2` を割り当てた結果はおよそ20%起き、`0.8` を割り当てた結果はおよそ80%起きるべきである。

人が好む答えを作るよう学習させたのがRLHF、検証可能な推論をさせたのがRLVRだとすれば、TypeSafeが行ったという **RLCD** は **その数字が意味を持つように** 学習させたものです。*Reinforcement Learning for Calibrated Decisions.*

## オープンモデルでもできるのか：SemIf

Jevは非公開モデルで、ホスティングサービスです。専用モデルなしでも同じインターフェースを作れるのか。`SemIf` というオープンソースがそれを実験しています。

着眼点がいいところです。モデルが `"billingです"` を作る **直前に**、内部にはすでに候補トークンごとのスコアがあります。それなら、わざわざトークンを生成する理由がないというわけです。

> 一度のフォワードパスを実行し、決められた大文字の解答トークンのlogitsにだけsoftmaxを適用する。**トークンを一つもデコードしない。**

ただし、線を一つ引いておく必要があります。

> このプロジェクトはその **インターフェースのパターン** をオープンモデルで再現する。Jevの非公開のモデルや学習方法を再現するものではない。

Jevの内部構造は公開されていません。二つは同じ技術ではなく、**同じ方向を違う位置から見せている** プロジェクトです。

## 二つを並べて回してみた

読むだけでは掴めないので、実際に動かしました。先ほどのチケットに真偽の質問を8個投げ、同じ入力を **Jev API** と、Mac Studio（64GB）にダウンロードして動かした **SemIf**（Qwen3.5-4B、MLX）の両方に送りました。

| 条件 | Jev | SemIf (Qwen3.5-4B) |
|---|---|---|
| 返金を求めているか | 0.99 | 0.999 |
| 重複決済か | 0.97 | 0.999 |
| **怒っているか** | **0.30** | **0.679** |
| 期限に言及しているか | 0.22 | 0.018 |
| セキュリティ事故か | 0.05 | 0.148 |
| 解約を求めているか | 0.02 | 0.014 |
| 注文番号があるか | 0.99 | 0.993 |
| ポリシーの対象か | 0.98 | 0.998 |

明白な7個は、どちらも同じ判断でした。

**割れたのは「怒っているか」一つです。** Jevは0.30で違うと見て、SemIfは0.679でそうだと見ました。丁寧に書いてはいるものの、二回請求されて早く処理してほしいという文面なので、人が見ても割れるところです。

大事なのは **どちらも確信していない** 点です。0.30も0.679も、0や1の近くではありません。判断は割れましたが、どちらも「曖昧だ」と言っています。

## 同じモデルに二通りで聞いてみると

ここまでは違うモデル同士の比較なので、条件が混ざっています。そこで **同じQwen3.5-4B** に同じ質問を二つの経路で聞きました。一つはQwenに直接、普通に答えを生成させるほう。もう一つはSemIfを通して、logitsを直接読むほうです。

違いは **確率を聞いたとき** に出ました。「各項目が真である確率を0〜1の数値でくれ」と指示してみました。

| 条件 | Qwenに直接（生成） | SemIfを通して（logits） |
|---|---|---|
| 返金を求めているか | 1.00 | 0.999 |
| **怒っているか** | **0.90** | **0.679** |
| 期限に言及しているか | 0.00 | 0.018 |
| **セキュリティ事故か** | **0.00** | **0.148** |
| 解約を求めているか | 0.00 | 0.014 |
| ポリシーの対象か | 1.00 | 0.998 |

**生成させた数字は三種類しかありません。** `0.00` か `0.90` か `1.00`。同じモデルのlogitsから読むと、0.018、0.148、0.679、0.993のように値が散らばるのに。

とくに「怒っているか」を見てください。言葉で答えさせると **0.90だと確信する** のに、自分の内部の値は **0.679** で曖昧だと言っています。同じモデルが、同じ質問に対してです。セキュリティ事故も、言葉では `0.00` ですが内部は0.148です。

**モデルが言う確信と、モデルが実際に持っている確信が違います。**

速度も測りました。ローカルの二行は同じMac Studioで **同じモデル** を使い、モデルを読み込む時間は除いて、それぞれ5回の中央値です。

| 方式 | 8件の処理 | 生成トークン |
|---|---|---|
| **Jev**（API・ネットワーク往復を含む） | **0.29秒** | 0 |
| ローカルモデルに普通に聞く（JSON生成） | 0.51秒 | 17 |
| **SemIf**（ローカル・同じモデル） | 0.59秒 | 0 |

**Jevがいちばん速いです。** ネットワークを往復してもです。ただし他社のサーバーで動くものなので、ローカルの二行と同じ線に並べて比べることはできません。

**ローカル同士では大きな差がありません。** 生成0.51秒、SemIf0.59秒。SemIfが報告した5.21倍は、条件が21個で生成側が111トークンを吐く状況でした。今回はそれより簡単な実験なので、速度の差が出なかった可能性があります。

## おわりに：これからは構造化された入力が重要になるのか

AIにJSONで答えさせることは、もう馴染みがあります。スキーマを渡し、形式に合っているか検査して。ところがそれは **出す側** だけを整えたものでした。入れる側は相変わらず文章の塊のままです。

Jevがもう一段求めるのは **入れる側** です。ドキュメントにこう書かれています。

> 値がデータベースから来たものなら、文字列テンプレートに差し込まず、その値専用のフィールドに入れよ。

> ほとんどのリクエストにはオブジェクトを使え。そうすれば状態の各部分が名前を持ち、互いの関係がはっきりする。

プロンプトをうまく書く問題ではなく、**持っているデータをどんな形で抱えているか** の問題に移ったわけです。

LLMが出てきたとき期待したのは、こういうことでした。デジタルになった文字さえ入れれば、あとは勝手にやってくれるだろう。ところが使ってみると、なかった話を作り、思ったより遅く、思ったより高い。その限界を一つずつ感じ始めた時期に、Jevのようなものが出てきました。

だからこれから分かれ目になるのは、モデルではないかもしれません。**自分たちが持っている情報とデータを、どれだけうまく構造化してあるか。** モデルがそのまま読める形に整えておくほうです。性能もコストも、そこで分かれるでしょう。

文書を扱う仕事なら、他人事ではありません。どのみち毎日やっているのが、散らばったものを構造にする仕事なのですから。その構造が人のためのものだったなら、これからはモデルにそのまま渡せるものでもあります。
