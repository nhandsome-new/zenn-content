*이 블로그는 에이전트가 자료 대조와 실험을 거쳐 초안을 작성하고, 필자의 검수를 거쳐 게재됩니다.*

:::message
**세 줄 요약**
- 프로그램이 필요한 건 `if` 하나인데, 우리는 LLM에게 문장을 만들게 한 뒤 그 문장을 다시 `if`로 되돌리고 있습니다
- `Jev`는 아예 문장을 만들지 않고 **판단과 확률**만 돌려주는 모델입니다. 그 설계를 정리했습니다
- 같은 질문을 Jev와 오픈소스 구현(SemIf) 양쪽에 돌려본 결과도 실었습니다
:::

지원 티켓 하나를 어느 팀으로 보낼지 정하는 코드를 생각해 봅니다. 프로그램이 알고 싶은 건 결국 한 줄입니다.

```python
if department == "billing":
```

그런데 LLM에게 시키는 일은 이렇습니다. 프롬프트 → 문장 생성 → JSON → 스키마 검증 → 파싱 → 실패하면 재시도 → 그제서야 `if`. **필요한 건 값 하나인데 문장을 한 바퀴 돌았습니다.**

![Jev와 SemIf는 같은 약속(state와 타입 있는 질문을 받아 확률을 돌려준다)을 공유하지만, Jev는 전용 비공개 모델이고 SemIf는 기존 오픈 모델의 logits를 읽는 오픈소스다.](/images/semantic-if/semantic-if-flow-ko.png)

## Jev — 문장 대신 확률을 주는 모델

이 문제를 정면으로 들고나온 게 TypeSafe라는 회사의 `Jev`입니다. 공식 문서([docs.typesafe.ai](https://docs.typesafe.ai/introduction))의 표현이 직설적입니다.

> 텍스트 생성도, 파싱도 없다. 코드가 바로 분기하고 정렬하고 라우팅할 수 있는 타입 있는 값과 확률분포를 받는다.

쓰는 방식부터 다릅니다. 프롬프트를 문장으로 조립하지 않습니다. 애플리케이션이 이미 들고 있는 JSON을 **상태(state)** 로 그대로 넘기고, 그 상태에 대해 **물어볼 것들을 타입으로** 정의합니다.

```python
response = client.system_one(
    state=ticket,                   # 앱의 JSON을 그대로
    questions={
        "department": Choice(...),  # 어느 팀으로 보낼까
        "frustration": Score(...),  # 불만도는 어느 정도인가
        "is_urgent": Noul(...),     # 긴급한가
    },
)
response.answers["is_urgent"].noul  # 0.94
```

보통은 DB에 있는 값을 이렇게 문장으로 풀어서 넣습니다.

```text
고객 등급은 enterprise이고 국가는 일본입니다.
주문 A-104에 49달러 결제가 두 건 있으며 둘 다 captured 상태입니다.
중복 결제는 환불 정책상 환불 대상입니다.
고객은 "49달러가 두 번 청구됐으니 중복분을 빨리 환불해 달라"고 썼습니다.
```

그런데 애플리케이션에는 이미 이런 게 있습니다.

```json
{
  "ticket": {
    "subject": "Charged twice for one order",
    "message": "I was charged 49 dollars two times for order A-104.
                Please refund the duplicate as soon as possible."
  },
  "customer": { "plan": "enterprise", "country": "Japan" },
  "order": {
    "id": "A-104",
    "charges": [
      { "amount": 49, "status": "captured" },
      { "amount": 49, "status": "captured" }
    ]
  },
  "refund_policy": { "duplicate_charge": "eligible" }
}
```

이 티켓은 뒤에서 실제로 Jev와 SemIf에 보낸 것이기도 합니다.

두 번째 쪽은 **구조가 곧 정보**입니다. `charges`가 배열이고 항목이 둘이라는 사실 자체가 "두 번 결제됐다"를 말합니다.

문장으로 풀면 이 구조를 모델이 다시 복원해야 합니다. 그리고 답은 또 JSON으로 달라고 하죠. **Jev는 그 왕복을 없앱니다.**

질문 여러 개를 **한 번에, 서로 독립적으로** 보낸다는 점도 눈여겨볼 만합니다. 위 코드에서 `frustration`은 `department`가 뭘로 나왔는지 모릅니다. 세 질문이 각자 같은 티켓만 보고 따로 답합니다.

흔히 쓰는 방식은 다릅니다. 한 번 답하고, 그 답을 넣어 다음을 묻고, 또 그 답을 보고 판단하죠.

![이어서 묻기와 따로 묻기 — 연쇄 방식은 앞의 답이 다음 질문에 들어가 요청이 세 번이지만, Jev는 같은 상태를 세 질문이 각자 읽어 요청이 한 번이고 서로의 답을 모른다.](/images/semantic-if/semantic-if-independent-ko.png)

독립적이면 앞 판단이 틀려도 **뒤로 번지지 않고**, 하나를 고쳐도 나머지가 흔들리지 않습니다. 이상한 답이 나오면 **그 질문만** 보면 됩니다.

대신 조합은 코드의 몫입니다.

```python
if category == "billing": ...
if urgent > 0.8:      priority += 1
if frustration > 1.5: priority += 1
```

그래서 **AI가 제어 흐름을 갖지 않습니다.** 요즘 에이전트는 모델이 생각하고 도구를 고르고 다시 생각하는 식이라 흐름을 모델이 쥡니다. Jev는 반대입니다. 순서·임계값·가중치는 코드에 남고, 모델은 자연어를 읽는 좁은 판단만 맡습니다. 기준이 바뀌면 프롬프트를 다시 짜는 대신 숫자 하나를 고칩니다.

## 세 가지 판단 — Choice · Score · Noul

Jev는 판단을 세 종류로만 나눕니다. 작고 조합 가능한 부품에 가깝습니다.

| | 쓰는 자리 |
|---|---|
| **Choice** | 순서 없는 후보 중 하나 — billing / access / technical |
| **Score** | 순서 있는 척도 — 평온 → 불편 → 불만 → 분노 |
| **Noul** | 명제가 참인가 — 환불을 요구하는가 |

앞의 티켓에 세 종류를 한 번에 물었더니 이렇게 왔습니다.

```json
"queue": {
  "choice": "billing",
  "confidence": 1.0,
  "probabilities": { "billing": 1.0, "technical": 0.0, "access": 0.0 }
}

"frustration": {
  "score": 0.71,
  "confidence": 0.6,
  "legend":        { "0": "Calm", "1": "Annoyed", "2": "Frustrated", "3": "Angry" },
  "probabilities": { "0": 0.34,   "1": 0.61,      "2": 0.05,         "3": 0.0 }
}

"refund": { "noul": 0.99 }
```

**Choice**는 고른 값만 주지 않고 후보별 분포를 통째로 줍니다. 1등만 볼 수도, 2등과 격차가 좁을 때만 사람에게 넘길 수도 있습니다.

**Score**의 `0.71`은 정수 레벨이 아닙니다. *Calm* 0.34에 *Annoyed* 0.61이 걸려 있으니 둘 사이에 떨어진 값입니다. 문서가 말한 *"레벨과 레벨 사이"*가 이겁니다. `legend`가 같이 와서 그 숫자가 무슨 뜻인지도 알 수 있습니다.

**Noul**은 필드가 하나뿐입니다. `confidence`가 없는데, 확률 자체가 확신이니 따로 줄 게 없죠. 가장 `if`에 가까운 형태입니다.

여기서 따라오는 원칙이 **질문을 잘게 쪼개라**는 것입니다. "위험도를 평가하고 어느 팀이 어떤 우선순위로 처리할지 정해라" 같은 큰 질문 대신 작은 질문 여럿으로요. 그래야 각각을 따로 보고 고칠 수 있습니다.

## 0.9가 90%가 되도록 — RLCD

확률을 값으로 쓰려면 걸리는 문제가 있습니다. 모델이 `0.9`라고 했을 때, 정말 10번 중 9번 맞는다는 뜻인가?

실무에서 임계값 긋기가 고단한 이유가 여기 있습니다. **`0.8`이라는 숫자에 뜻이 없어서**, 라벨 붙인 데이터를 모아 놓고 0.7로 해보고 0.85로 해보며 선을 찾습니다. 태스크가 바뀌면 처음부터 다시 하고요.

> 확률 `0.2`를 부여한 결과는 약 20% 정도 일어나야 하고, `0.8`을 부여한 결과는 약 80% 일어나야 한다.

사람이 선호하는 답을 만들게 학습한 게 RLHF, 검증 가능한 추론을 시킨 게 RLVR이라면, TypeSafe가 했다는 **RLCD**는 **그 숫자가 의미를 갖도록** 학습한 것입니다. *Reinforcement Learning for Calibrated Decisions.*

## 오픈 모델로도 되나 — SemIf

Jev는 비공개 모델이고 호스팅 서비스입니다. 전용 모델 없이도 같은 인터페이스를 만들 수 있을까요. `SemIf`라는 오픈소스가 그걸 실험합니다.

착안점이 좋습니다. 모델이 `"billing입니다"`를 만들기 **직전에**, 내부에는 이미 후보 토큰마다 점수가 있습니다. 그렇다면 굳이 토큰을 생성할 이유가 없다는 거죠.

> 한 번의 순전파를 수행하고, 정해진 대문자 답안 토큰들의 logits에만 softmax를 적용한다. **토큰을 하나도 디코딩하지 않는다.**

다만 선을 하나 그어둬야 합니다.

> 이 프로젝트는 그 **인터페이스 패턴**을 오픈 모델로 재현한다. Jev의 비공개 모델이나 학습 방식을 재현하는 것이 아니다.

Jev의 내부 구조는 공개돼 있지 않습니다. 둘은 같은 기술이 아니라 **같은 방향을 다른 위치에서 보여주는** 프로젝트입니다.

## 둘을 나란히 돌려봤다

읽기만 해서는 감이 안 와서 직접 돌렸습니다. 앞의 티켓에 참·거짓 질문 8개를 물었고, 같은 입력을 **Jev API**와, 맥 스튜디오(64GB)에 받아 돌린 **SemIf**(Qwen3.5-4B, MLX) 양쪽에 보냈습니다.

| 조건 | Jev | SemIf (Qwen3.5-4B) |
|---|---|---|
| 환불을 요구하는가 | 0.99 | 0.999 |
| 중복 결제인가 | 0.97 | 0.999 |
| **화났는가** | **0.30** | **0.679** |
| 기한을 언급하는가 | 0.22 | 0.018 |
| 보안 사고인가 | 0.05 | 0.148 |
| 해지를 요구하는가 | 0.02 | 0.014 |
| 주문번호가 있는가 | 0.99 | 0.993 |
| 정책 대상인가 | 0.98 | 0.998 |

명백한 7개는 둘 다 같은 판단이었습니다.

**갈린 건 "화났는가" 하나입니다.** Jev는 0.30으로 아니라고, SemIf는 0.679로 맞다고 봤습니다. 정중하게 쓰긴 했지만 두 번 청구됐고 빨리 처리해 달라는 글이니 사람이 봐도 갈릴 만합니다.

중요한 건 **둘 다 확신하지 않는다**는 점입니다. 0.30도 0.679도 0이나 1 근처가 아닙니다. 판단은 갈렸지만 둘 다 "애매하다"고 말하고 있습니다.

## 같은 모델에게 두 가지로 물어보면

여기까지는 다른 모델끼리의 비교라 조건이 섞여 있습니다. 그래서 **같은 Qwen3.5-4B**에 같은 질문을 두 경로로 물었습니다. 하나는 Qwen에게 직접 — 평범하게 답을 생성시키는 쪽. 다른 하나는 SemIf를 통해 — logits를 직접 읽는 쪽입니다.

차이는 **확률을 물었을 때** 드러났습니다. "각 항목이 참일 확률을 0~1 숫자로 달라"고 시켜 봤습니다.

| 조건 | Qwen에게 직접 (생성) | SemIf를 통해 (logits) |
|---|---|---|
| 환불을 요구하는가 | 1.00 | 0.999 |
| **화났는가** | **0.90** | **0.679** |
| 기한을 언급하는가 | 0.00 | 0.018 |
| **보안 사고인가** | **0.00** | **0.148** |
| 해지를 요구하는가 | 0.00 | 0.014 |
| 정책 대상인가 | 1.00 | 0.998 |

**생성시킨 숫자는 세 종류뿐입니다.** `0.00` 아니면 `0.90` 아니면 `1.00`. 같은 모델의 logits에서 읽으면 0.018, 0.148, 0.679, 0.993처럼 값이 흩어지는데 말이죠.

특히 "화났는가"를 보세요. 말로 답하라면 **0.90이라고 확신**하는데, 자기 내부 값은 **0.679**로 애매하다고 합니다. 같은 모델이 같은 질문에 대해서요. 보안 사고도 말로는 `0.00`이지만 내부는 0.148입니다.

**모델이 말하는 확신과 모델이 실제로 가진 확신이 다릅니다.**

속도도 재봤습니다. 로컬 두 줄은 같은 맥 스튜디오에서 **같은 모델**로, 모델 올리는 시간은 빼고, 각각 5회 중앙값입니다.

| 방식 | 8건 처리 | 생성 토큰 |
|---|---|---|
| **Jev** (API · 네트워크 왕복 포함) | **0.29초** | 0 |
| 로컬 모델에 그냥 물어보기 (JSON 생성) | 0.51초 | 17 |
| **SemIf** (로컬 · 같은 모델) | 0.59초 | 0 |

**Jev가 제일 빠릅니다.** 네트워크를 타고 갔다 오는데도요. 다만 남의 서버라 로컬 두 줄과 같은 선에 놓고 비교할 수는 없습니다.

**로컬끼리는 큰 차이가 없습니다.** 생성 0.51초, SemIf 0.59초. SemIf가 보고한 5.21배는 조건이 21개이고 생성 쪽이 111토큰을 뱉는 상황이었습니다. 이번에는 그보다 간단한 실험이라 속도 면에서의 차이가 드러나지 않았을 가능성이 있습니다.

## 마무리 — 앞으로는 구조화 인풋이 중요해질까

AI에게 JSON으로 답하게 만드는 일은 이제 익숙합니다. 스키마를 주고, 형식에 맞는지 검사하고. 그런데 그건 **나오는 쪽**만 정리한 것이었습니다. 넣는 쪽은 여전히 문장 한 덩어리였죠.

Jev가 한 겹 더 요구하는 건 **들어가는 쪽**입니다. 문서에 이렇게 적혀 있습니다.

> 값이 데이터베이스에서 온 것이라면, 문자열 템플릿에 끼워 넣지 말고 그 값만의 필드에 넣어라.

> 대부분의 요청에는 객체를 써라. 그래야 상태의 각 부분이 이름을 갖고, 서로의 관계가 분명해진다.

프롬프트를 잘 쓰는 문제가 아니라, **가진 데이터를 어떤 모양으로 들고 있느냐**의 문제로 옮겨간 셈입니다.

LLM이 나왔을 때 기대한 건 이런 것이었습니다. 디지털로 된 글자만 넣으면 나머지는 알아서 해주겠지. 그런데 써 보니 없던 말을 지어내고, 생각보다 느리고, 비쌉니다. 그 한계를 체감하던 시점에 Jev 같은 것이 나왔습니다.

그래서 앞으로 갈리는 지점은 모델이 아닐지도 모릅니다. **우리가 가진 정보와 데이터를 얼마나 잘 구조화해 두었는가** — 모델이 그대로 읽을 수 있는 모양으로 정리해 두는 쪽이요. 성능도 비용도 거기서 갈릴 겁니다.

문서를 다루는 업무라면 남의 이야기가 아닙니다. 어차피 매일 하는 일이 흩어진 것을 구조로 만드는 일이니까요. 그 구조가 사람이 읽기 위한 것이었다면, 이제는 모델에게 그대로 건넬 수 있는 것이기도 합니다.
